= Live task checks

Slurm-web can display structured checks emitted independently by every task in a job.
Checks, task output, GPU telemetry and job state are delivered to the browser over one
multiplexed WebSocket per job. A Server-Sent Events (SSE) stream and polling endpoints
remain available as a fallback, and the snapshot stays available after the job finishes.

== Emit a check

Install `contrib/slurm-check` on compute nodes and make a shared directory available to
the Slurm-web agent at `/mnt/ai-data/.slurm-web/checks`.

[source,console]
----
$ slurm-check running load-model "Load model" --progress 25 \
    --message "Loading shard 7/29"
$ slurm-check passed load-model "Load model" --duration-ms 31042 \
    --message "29 shards loaded"
----

The command reads `SLURM_JOB_ID`, `SLURM_STEP_ID`, `SLURM_PROCID` and
`SLURMD_NODENAME`. These values can also be specified explicitly with `--job`,
`--step`, `--task` and `--node` for testing.
Events are silent on standard output so task logs remain clean. Use `--print-event` for
CLI debugging.

Each task writes its own append-only JSONL file:

[source,text]
----
<root>/<job>/<step>/task-<rank>.jsonl
----

This avoids concurrent append operations from multiple compute nodes. Supported states
are `queued`, `running`, `passed`, `failed`, `warning`, `skipped` and `cancelled`.
Running checks without an update for 15 seconds are rendered as `stalled`.

== Log sections and failure summary

The job output pane renders like a CI job log: numbered lines, ANSI colors,
search, follow, stdout/stderr tabs and collapsible sections. Sections use the
GitLab marker format, so `slurm-check section start NAME [TITLE]` and
`slurm-check section end NAME` fold a phase of the task and show its duration;
GitHub `::group::` / `::endgroup::` markers are recognised as well. Pipeline
stages whose name matches a section jump to it.

When a job ends in failure, the agent extracts an error excerpt from the tail of
stderr (or stdout when Slurm merged the streams): the last `Traceback`, CUDA out of
memory, `srun: error` or similar line and what follows. It is exposed as
`GET /api/agents/<cluster>/job/<job>/diagnostics` together with the exit code,
derived exit code, signal and failed steps, and pushed on the live `job` channel.
`GET /api/agents/<cluster>/job/<job>/log?stream=stdout&raw=1` downloads the whole
output file.

== Live WebSocket

The job workbench opens a single WebSocket:

[source,text]
----
ws(s)://<gateway>/api/agents/<cluster>/job/<job>/live
----

Browsers cannot set the `Authorization` header on a WebSocket, so the first frame
carries the bearer token instead of putting it in the URL:

[source,json]
----
{"type": "auth", "token": "<jwt>"}
{"type": "subscribe", "channels": ["checks", "log", "gpu", "job"],
 "checks_cursor": 0, "log": {"stream": "stdout", "offset": 0}}
----

The gateway validates the token, opens one upstream WebSocket to the agent with the
same token in the `Authorization` header, and relays frames verbatim in both
directions. The agent owns the session:

* `checks`: a `checks` snapshot on subscribe, then one `check` frame per new event.
  Events resume from `checks_cursor` (the event sequence number).
* `log`: subscribe with `"log": {"streams": {"stdout": 0, "stderr": 0}}` (one
  byte offset per stream; the legacy `stream`/`offset` pair is still accepted).
  `log` frames carry only new bytes per stream, `merged: true` says Slurm wrote
  stderr into stdout, and `{"type": "pause"|"resume", "channel": "log"}` holds
  the stream without losing offsets.
* `gpu`: the latest per-GPU telemetry every two seconds, only when it changed.
  Nothing is buffered, so a slow client never receives a backlog of stale frames.
* `job`: state, elapsed time, nodes and steps, only when they changed.
* `heartbeat` every ten seconds of silence; `ping` is answered with `pong`.

Authorization failures close the socket with code `4401`, `4403` or `4404`; protocol
errors use `4400` and an unreachable agent `4502`. The client reconnects with its
cursors after network failures and falls back to SSE and polling when the WebSocket
cannot be established at all.

Every long-lived session occupies one Gunicorn thread in the agent and one in the
gateway. Container images therefore default to `gthread` workers with 32 threads
(`SLURMWEB_THREADS`). The data roots can be relocated with `SLURMWEB_CHECKS_ROOT`,
`SLURMWEB_LOG_ROOTS` (colon separated) and `SLURMWEB_GPU_ROOT`.

== Fallback APIs

The current snapshot is available from:

[source,text]
----
GET /api/agents/<cluster>/job/<job>/checks
----

Incremental updates use a resumable cursor:

[source,text]
----
GET /api/agents/<cluster>/job/<job>/checks/events?cursor=<sequence>
----

The SSE connection emits `check` events and a heartbeat every ten seconds. Task output
and GPU telemetry can also be polled from `/job/<job>/log` and `/job/<job>/gpus`.
